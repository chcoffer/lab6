# SplitSmart Constitution

## Core Principles

### I. Customer-Driven Requirements
The SplitSmart customer request in UserRequirement.md is the authoritative definition of required behavior. Customer requirements define what the system must deliver; implementation decisions define how the system is built. Product and engineering work MUST trace every requirement to a user-visible behavior, acceptance criterion, or validation artifact before it is accepted as complete.

This distinction prevents scope drift. A requirement such as expense tracking, permissioned access, balance reconciliation, or notifications is non-negotiable business intent. Technology choices such as Java 21, Maven, Java Swing, JUnit 5, or PlantUML are implementation decisions chosen to satisfy those requirements and MUST NOT be treated as customer requirements themselves.

### II. Object-Oriented Design & Separation of Concerns
All domain logic MUST be designed using sound object-oriented principles: clear responsibilities, encapsulation, explicit collaboration, and maintainable abstractions. The system MUST separate business rules from presentation logic, user interaction, and persistence concerns so that the domain model remains testable and independent of GUI code.

A GUI component may present data and collect user input, but it MUST NOT contain the authoritative logic for expense calculation, balance settlement, approval decisions, or rule enforcement. Business rules belong in domain or service classes, while the UI remains a thin interface to those rules.

### III. Money & Data Integrity
All monetary values MUST be represented with BigDecimal and MUST NOT be calculated with floating-point types. Expense totals, allocations, balances, and payments MUST use explicit rounding and precision rules that are consistent, documented, and auditable.

The project MUST preserve financial correctness over convenience. Balance calculations, settlement operations, reports, and approval workflows MUST be deterministic and verifiable from the underlying source data, with no hidden or implicit rounding behavior.

### IV. Verification & Traceability
Every customer requirement MUST have a clear traceability path to implementation evidence. Feature work MUST include or reference the corresponding tests, design notes, and acceptance checks needed to verify the behavior. Requirements without traceability are considered incomplete.

JUnit 5 MUST be used for automated verification of business logic and regression scenarios. PlantUML MAY be used to document the domain model, workflow, and architectural relationships when the diagram clarifies required behavior or system boundaries. The project MUST maintain enough evidence for human review to confirm that each requirement is implemented and tested.

### V. Human Review & AI Governance
AI-generated code, diagrams, tests, requirements analysis, and documentation are assistive tools, not authoritative decisions. Human reviewers MUST evaluate AI output for correctness, requirement alignment, architectural fit, operational risk, and financial integrity before it is accepted.

No artifact may bypass review simply because it was generated by AI. The team MUST treat AI output as an initial draft requiring verification against the SplitSmart customer requirements, implementation constraints, and this constitution. Human review is mandatory for any approval workflow, requirement interpretation, or output that affects financial records or user trust.

## Technology Constraints
The implementation MUST follow these constraints unless a later governance amendment explicitly changes them:

- Java 21 is the target runtime baseline for the application and its supporting libraries.
- Maven is the build and dependency management standard for the project.
- Java Swing is the default GUI technology for the desktop implementation unless a formal project decision supersedes it.
- JUnit 5 is the required test framework for automated validation.
- PlantUML is permitted for architectural and process documentation when it improves clarity and traceability.
- Object-oriented design is required to keep the domain model clear, extensible, and maintainable.
- GUI and business logic MUST remain separated to preserve testability and reduce coupling.
- Monetary values MUST use BigDecimal for calculations and reporting.
- Requirement traceability MUST be maintained throughout design, implementation, and review.

## Quality Gates
Every change that affects the SplitSmart product or its governing rules MUST pass a human review before acceptance. Reviewers MUST confirm that the change aligns with the customer requirement, preserves separation of concerns, keeps money handling exact, and maintains traceability from requirement to verification.

The project MUST prioritize correctness over speed. Work may not be marked complete if the requirement-to-test evidence is missing, if the business logic is coupled to the GUI, or if the system cannot demonstrate safe handling of financial data. Approval workflows, reports, and settlement logic require extra scrutiny because they directly affect user trust and reconciliation accuracy.

## Governance
This constitution governs the SplitSmart project and supersedes ad hoc decisions that conflict with it. Amendments require written rationale, explicit version updates, and a human review confirming that the new guidance remains consistent with the customer request and with the project’s non-negotiable principles.

Any proposed change MUST identify whether it modifies a requirement, an implementation decision, or a governance rule. Requirement changes MUST be traceable to the original customer intent; implementation changes MUST remain subordinate to those requirements; and constitutional changes MUST include a clear explanation of why the new rule is necessary.

Compliance review is mandatory for any change affecting expense logic, balance processing, approvals, notifications, reporting, user access, or AI-assisted work. The project MUST treat governance violations as defects to be corrected before release or approval.
