# ChatGPT Prompt — Independent SplitSmart Architecture Review

You are acting as an independent Principal Software Architect and Technical Architecture Reviewer.

Your responsibility is to evaluate two independently developed architectures for the SplitSmart application.

Be objective, technically rigorous, and evidence-driven. Do not favor one architecture simply because it uses a particular architectural pattern or was generated by a particular AI tool.

Your goal is to determine which architecture best satisfies the actual project requirements and provides the best foundation for implementation.

## 1. Review Materials

Examine the following materials.

### Original Project Requirements

Repository: https://github.com/chcoffer/lab6

Read:
- Project constitution.
- SplitSmart feature specification.
- Functional requirements.
- Non-functional requirements.
- Java Swing MVP requirements.
- Success criteria.
- Existing assumptions and clarifications.

### Architecture A — Spec Kit

Locate and review the architecture generated through Spec Kit.

Expected approach: Layered Architecture with MVC.

Review all associated documents, diagrams, database designs, technology decisions, and implementation planning artifacts.

### Architecture B — Codex

Locate and review the architecture generated through Codex.

Expected approach: Clean Architecture with Hexagonal Architecture and Domain-Centered Design.

Review all associated documents, diagrams, database designs, technology decisions, and implementation planning artifacts.

If required documents are missing, explicitly identify them. Do not assume missing information exists.

## 2. Establish Evaluation Criteria

Evaluate both architectures using the same criteria and this weighted scoring system.

| Evaluation Category | Weight |
|---|---:|
| Requirements coverage | 15% |
| Architectural correctness | 15% |
| Maintainability | 10% |
| Testability | 10% |
| Financial integrity | 15% |
| Security and authorization | 10% |
| Extensibility and scalability | 10% |
| Implementation complexity | 5% |
| Technology suitability | 5% |
| Documentation quality | 5% |
| **TOTAL** | **100%** |

Score each category from 1 to 10.

Calculate the weighted total on a 100-point scale.

Explain each score with evidence from the architecture documents. Do not award high scores based solely on architectural terminology or diagram quality.

Verify whether each architecture addresses the original requirements.

Pay particular attention to:
- User accounts and authentication.

- Invitation-based group membership.

- Equal and percentage splitting.
- Receipt image handling.
- Notifications.

- Reporting.
- Data privacy.
- Historical financial records.
- Web, Android, and iOS expansion.
- Java Swing desktop MVP.

Identify requirements that are fully addressed, partially addressed, missing, or addressed through unsupported assumptions.

Produce a requirements traceability matrix.

## 4. Financial Integrity Review

Inspect how each architecture handles financial calculations and data consistency.

Verify:
1. Monetary precision and decimal representation.
2. Equal splitting.
3. Percentage splitting.
4. Rounding to two decimal places.
5. Remaining-cent allocation.
6. Validation of positive amounts.
7. Validation that percentages total 100%.
8. Approval before balance adjustments.
9. Payment settlement.
10. Historical transaction records.
11. Concurrent transactions.
12. Duplicate transaction prevention.
13. Partial failures and rollback.

Determine whether each design can keep financial transactions internally consistent.

Identify weaknesses that could cause incorrect balances or financial discrepancies.

## 5. Technical Architecture Review

Evaluate the internal consistency of each architecture.

Review:
- Component boundaries.
- Separation of responsibilities.
- Dependency direction.
- Domain model.
- Database design.
- Service interfaces.
- Data access.
- Error handling.
- Authentication and authorization.
- Transaction management.
- Logging and auditing.
- Testing strategy.
- Deployment considerations.

Identify:
- Circular dependencies.
- Unnecessary abstractions.
- Overengineering.
- Tightly coupled components.
- Missing interfaces.
- Unclear responsibilities.
- Architectural contradictions.
- Technology decisions without sufficient justification.

Check that diagrams accurately represent the written architecture.

## 6. Java Swing MVP Suitability

Determine whether each architecture is appropriate for the actual desktop MVP.

Evaluate:
- Ease of implementing Java Swing interfaces.
- Separation of GUI and business logic.
- Ease of testing business rules independently.
- Database integration.
- Development complexity.
- Suitability for a small development team.

Do not penalize an architecture for not implementing the full future web/mobile platform in the desktop MVP.

Assess whether its design creates unnecessary obstacles to future expansion.

## 7. Future Expansion Review

- Remote database access.
- API-based integration.
- External notification providers.

Distinguish between capabilities already supported by the architecture and capabilities requiring significant redesign.

- Be independent and objective.
- Do not assume either architecture is correct.
- Use the original project specification as the authoritative source of requirements.
- Treat the project constitution as authoritative for technology and development constraints.
- Do not invent features.
- Do not confuse architectural sophistication with architectural quality.
- Do not overlook implementation complexity.
- Do not ignore financial correctness.
- Cite specific files, sections, and diagrams supporting findings.
- Clearly distinguish facts, assumptions, and recommendations.
- Do not modify either architecture during the review.
